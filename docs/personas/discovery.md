# Discovery — Silica UI

**Product, in the customer's words:** "A set of ready-made, themeable UI pieces I drop
into my Tailwind project — and a visual builder I can put inside my own app so my
customers can lay out their own pages and emails."

**The promise with a number in it:** the README and the marketing site both put counts
on the box — "76 CSS component families", "90 React components", and on /about the
stat tiles read **113 Components · 34 Behaviors · 13 Packages · MIT**. Those three
numbers disagree with each other and with the code (116 demo pages, 117 React source
files, 35 behavior modules, 13 packages). Packages and MIT check out. The component
count does not. **Verify on the screen in P01 — do not pre-file.**

**The customer:** two genuinely different people, and the roster must carry both.
- A **developer** installing the packages into their own project. Technical. What they
  lose when it breaks: a day, and their trust in the system's defaults.
- A **business user** driving the embedded builder — memory note
  `navigator-business-user-naming` says the Navigator was deliberately reworded for
  them. Non-technical. What they lose: their own site or their own send.
- A third, smaller: the **host developer** embedding the builder (sparx, piggles).
Devices: the docs and the marketing site are read on phones. The builder is a desktop
tool but its OUTPUT is judged on a phone.

## The spine

There is **no signup and no account**. The spine every single customer walks is:

1. **silicaui.com `/`** — the marketing promise (apps/site, port 4011)
2. **`/docs`** — the component index
3. **`/docs/getting-started`** — the install instructions
4. **`pnpm add` + `@plugin "@wizeworks/silicaui"` in their own CSS** — the install
5. **first component on screen, in the right theme, in their own project**

Step 4 is the gap where "it said it worked and nothing happened" lives here: a CSS-first
plugin that is imported wrong renders an unstyled page with no error at all.

## Screens

Generated by `docs/personas/gen-screens.mjs` — see rating.md for the count and the
method. Three surfaces: the site (Next.js App Router routes, with the component doc
pages expanded 1:1 from `DEMO_META`), the playground (one page), and the builder
(panes, both surfaces).

The docs sidebar is generated from `DEMO_META` in `apps/site/src/lib/nav.ts`, so **no
doc page can be an orphan** — adding a demo adds its nav entry. That is a real strength
and it is why the "not reachable from any nav" section is short.

## Accounts

**None.** No signup, no password, no email, no database. Rules that assume an account
must be narrowed rather than kept:
- Rule #7's **isolation** half has no tenants to isolate. Its real analogue in this
  product is the **boundaries that must hold**: two-tier node `locked`, host-node lock,
  peer claims under `applyRemoteOps`, and the host sanitizer on `rawHtml`.
- Rule #7's **regression** half applies in full and is the more important half here.
- Rule #8's artifact is not an account's store — it is a **real working thing built on
  silicaui** that a stranger could use.

## Verifying what the UI claimed

No database. The read-only equivalents are:
- `packages/silicaui-builder` probes: `pnpm --filter @wizeworks/silicaui-builder verify`
  (24 named probes) — used to CONFIRM what a screen wrote, never to do the work.
- `pnpm --filter @wizeworks/silicaui-html golden` — the projection golden files.
- The silicaui MCP (`list_components`, `get_component`, `list_classes`, `get_theme`) —
  read-only catalog.
- Computed styles read back out of the page in Playwright — the honest way to check a
  token actually resolved, because a hex that looks right in one theme is the defect
  this whole system exists to stop.
