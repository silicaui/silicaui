**Status:** fixed
**Severity:** major
**Found by:** P04 · while registering a new screen during act 1
**Surface:** the framework itself — `docs/personas/gen-screens.mjs` → `rating.md`
**Filed:** 2026-09-19
**Fixed:** 2026-09-19
**Confirmed by:** see below
**Blocked on:** —

## What happened

Adding the email starter picker ([063](063-the-templates-panel-had-no-templates.md))
added a screen, so `pnpm verify` stopped — correctly:

```
gen-screens: these builder files are neither a screen nor explicitly excluded.
Classify each one in gen-screens.mjs — a denominator that silently stops
counting is worse than no denominator.
  src/email/react/EmailStarterDialog.tsx
```

That guard is good and it did its job. So I classified the file and ran the command it
told me to run. It then deleted **P01's entire scoring run**:

```
-| Home | `/` | 5 → 8 | 7 → 8 | now switches light/dark and follows the OS #002; … | P01 |
+| Home | `/` | — | — | | |
-| Docs | `/docs` | 4 → 8 | 3 → 8 | grouped into 8 real categories #007 … | P01 |
+| Docs | `/docs` | — | — | | |
```

Six scored rows, gone. A persona run's worth of judgement, from a completed run,
replaced with dashes by the tool whose whole purpose is to protect that file.

The only reason it came back is that it happened to be committed.

## What should have happened

Adding a screen adds a row. It does not touch any other row.

## How to reproduce

1. Score any row in `rating.md` by hand.
2. Run `node docs/personas/gen-screens.mjs`.
3. Before the fix: the score is gone.

## Why it matters

`rating.md` is one of the framework's three deliverables, and the scores in it are the
only record of judgement a run produces — the issues record defects, the artifact
records output, and this records *how good it is*. It is regenerated by a script, and
that script took a wrecking ball to it on a completely ordinary day.

**The file already knew.** Eleven lines above the bug, the `--check` path says so in as
many words:

> Scores and gaps are written **BY HAND** into the generated rows as runs happen, so a
> byte comparison would fail the moment anyone actually used the file. Compare the
> screen SET instead.

So the read path was written by somebody who understood exactly what lives in those
rows, and the write path immediately below it throws it all away. One of this
framework's own named failure shapes is **a fix that leaves its neighbour behind**;
this is that, eleven lines apart, in the framework.

It is also the worst kind of data loss: silent and successful. The command printed
`wrote 143 screens into rating.md` and exited 0.

## Where it lives

[docs/personas/gen-screens.mjs](../gen-screens.mjs)

```js
const next =
  current.slice(0, current.indexOf(START)) +
  generated +                                  // ← every row, blank
  current.slice(current.indexOf(END) + END.length);
writeFileSync(ratingPath, next);
```

## Do the siblings have it too?

| | |
| --- | --- |
| `gen-screens.mjs --check` | **correct** — compares the screen set, explicitly not the scores |
| `gen-screens.mjs` (write) | **the defect** |
| `gen-counts.mjs`, `gen-catalog.mjs` (the docs site) | checked: both write files that are wholly generated, with nothing hand-authored inside. Not the same case |

## The fix

**The write is a merge.** Hand cells are carried over by `name :: key`:

```js
const ROW = /^\| ([^|]+) \| `([^`]+)` \|(.*)/;
const hand = new Map();
for (const line of current.slice(current.indexOf(START), current.indexOf(END)).split(/\r?\n/)) {
  const m = line.match(ROW);
  if (!m) continue;
  const cells = m[3].replace(/\r$/, "").split("|");
  if (cells.length >= 4) hand.set(`${m[1].trim()} :: ${m[2]}`, cells.slice(0, 4).join("|"));
}
```

A row that already exists keeps its four hand cells; a new row arrives empty; a row
whose screen is gone disappears with it, which is right — that screen does not exist.

**And it refuses rather than guessing**, because the first version of this fix was
itself the same bug:

```js
if (hasBlock && current.includes("| Screen | Key |") && hand.size === 0) {
  console.error(
    "gen-screens: the existing block has rows but none parsed, so a rewrite would\n" +
      "throw away every score. Refusing.",
  );
  process.exit(1);
}
```

**The bug inside the fix, which is the interesting part.** My first merge anchored the
row regex with `$`. `rating.md` is **CRLF**, `.` does not match `\r`, so `(.*)$` never
matched a single row — the merge carried nothing over and reported success, wiping the
scores a second time. The `--check` path happens to be immune because it has no `$`.
So the guard above is not belt-and-braces; it is there because this exact mistake has
now been made twice in one hour, and the next person will make it too.

**Prose inside the block is still not preserved**, and cannot be — the block is rebuilt
section by section. So a note I had written under the builder heading was eaten as
well; it now lives **above** the BEGIN marker, and both the script and the file say
that is where notes go.
